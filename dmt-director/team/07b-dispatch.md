# §5.2 Appendix: dispatch prompt templates and pi hosting (low-frequency details; referenced on demand from `team/07-discipline.md` §5.2)

## Dispatch prompt skeleton (fill it in, do not improvise)

`You are a sub-agent of <role>. Skill: <the matching dmt-<role> skill name> (cbc calls it with the slash command; codex uses the same-named skill or '<skill dir>/dmt-<role>/SKILL.md'; pi reads '<skill dir>/dmt-<role>/SKILL.md' and executes per its mandatory-skills section). Unit: <one sentence>. Inputs: <paths>. Boundaries: <Files>. Artifacts: <paths and format>. Criteria: <testable>. Report: <format>. Timeout: <timeoutMs>. Build extras: <**mandatory whenever the ticket touches gradle / clean build**: this worktree needs `local.properties` (sdk.dir) plus symlinks for the two vendored directories under `app/src/main/jni/` (`opencv-mobile-4.13.0-android` / `ncnn-20260526-android-vulkan` → the same paths in the main repo; all gitignored, not deliverables) plus `ANDROID_HOME=<sdk path>; without them configureCMake reports `Could not find OpenCV` / `SDK location not found`>. **Material extras**: <**mandatory whenever a gate depends on "externally collected material" (e.g. device samples / JSON under `test/`)**: the material root path, the **override variable name** (e.g. `MATERIALS_ROOT` / `DEVICE_RESULTS`), and the behaviour when it is missing (it must **fail loud** and print the **absolute path of the material root actually used** plus a pointer to the fix)>. Resource discipline: **no `pkill <pattern>` / `pkill -f` / `killall`** (clean up only by the exact PID from your own pidfile) + **the same gate / the same worktree must not run concurrently** (check `ps` before rerunning a heavy gate; wait or move to another one). Close-out: **before merging you must run the gate once on a tree that lacks this ticket's local artifacts** (a **detached worktree** of the same main repo; **`archive` / `clone --shared` are forbidden** — they lack refs and produce false red); the evidence must include that reading. File-writing discipline: write with each harness's structured editing tool (codex uses `apply_patch`); an Edit's oldString must be unique.`

`<role>` ∈ `pde{n}` / `dev-e` / `ana-e`, with the matching skill `dmt-pde` / `dmt-de` / `dmt-ae`. The `reviewer{n}` variant is below.

## reviewer{n} variant (acceptance only; `/code-review` is a template constant — do not replace or omit it)

`You are devm's reviewer{n} sub-agent. Skill: dmt-reviewer (cbc calls it with the slash command; codex uses dmt-reviewer; pi reads '<skill dir>/dmt-reviewer/SKILL.md'). You must invoke <mandatory skill name: mattpocock-skills:code-review for codex, /code-review for the rest> and verify item by item. Independence: you must not be the same instance as the dev-e who implemented this ticket, you do not accept devm / dev-e conclusions, and you trust only ticket + SPEC + diff + evidence; a "pass" without evidence counts as a fail. Ticket: <ticket path>. SPEC: <matching spec-seq path>. Inputs: <diff, evidence, test output paths>. Criteria: check the ticket's acceptance criteria one by one, attaching an evidence path to each. Report: per-item pass/fail + verdict + evidence paths (the verdict is copied to the director along with devm's report for spot checks). Timeout: <timeoutMs>.`

## Codex harness hosting

A Codex role's skills come from the project's `.agents/skills/` (and `.codex/skills/`); mattpocock plugin skills are referenced as `mattpocock-skills:<name>`. The sub-agent dispatch template is:

`You are <spawner>'s <role> sub-agent. First read and execute the skill <skill path> in full, then read its mandatory skills: <qualified name or path>. Unit: <one sentence>. Inputs: <absolute paths>. Context paths: <only the external files that are needed>. Boundaries: <Files>. worktree: <absolute path of this ticket's worktree, created in advance by devm>. Artifacts: <paths and format>. Criteria: <testable>. Report: <format>. Timeout: <timeoutMs>. When done, report evidence only; do not merge / push yourself.`

Codex prefers `spawn_agent`; after dispatching, collect results with `wait_agent` in parallel. Start a new `spawn_agent` for a new unit; reuse the existing one only for corrections / narrowing of the same unit. A sub-agent must be given the role skill and input paths explicitly; never accept a bare claim of "already loaded". When Codex inside a herdr role pane has no `spawn_agent` interface, it must not fake a team by nesting `codex exec` through a shell: it does only its own pane role's work and records `[SUBAGENT_UNAVAILABLE]`.

## pi harness hosting (`delegate`)

`dev-e` / `ana-e` / `pde{n}` / `reviewer{n}` are **role semantic names**, not agent registration names in pi-subagents. The `agent` field of the pi workflow `runs.run/all` **must be set to the built-in hosting agent `delegate`** (no preset behaviour, inherits the parent model); dispatching by role name always reports `Unknown agent` (instance: on 2026-10-31 `agent:'ana-e'` failed three times out of three, and switching to `delegate` worked immediately). The role is set by writing "you are <spawner>'s <role> sub-agent" in the prompt; `agent` only handles hosting.

Under pi, `delegate` **has no skill list and no Skill tool** ⇒ you must give the skill file path in the prompt: `read <skill dir>/dmt-<role>/SKILL.md`, and then read the mandatory skills one by one with `read <skill dir>/<name>/SKILL.md`. cbc is not subject to this (a teammate `Agent` with a name carries the role name, inherits the skill list and can use the slash command directly).
