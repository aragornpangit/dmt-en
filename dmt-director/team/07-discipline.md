## 5. Discipline

### 5.1 Git

1. **`git add -A` / `git add .` are forbidden**; always list file paths explicitly when committing (prefer `git commit -m "..." -- <path>`, which bypasses the index), and insert no other action between `add` and `commit` (so the index cannot sweep in a concurrent writer's changes).
2. **The repository is managed by devm: merge and push belong to devm only** (**scope = the target project**: the push / merge ownership in this item constrains only the project repository managed by the dmt workflow; **it does not apply when maintaining the skill repositories themselves** such as `dmt` / `dmt-en`, see "Scope" in the file header): **only `devm` may run** `git push` and merge to the mainline (**push as soon as this department's `reviewer{n}` acceptance passes** — no need to wait for a notice from the director); `director` keeps the right to spot-check (devm still does the pushing after a spot check); `anam` / engineers **must never push or merge to the mainline**. Engineers (`dev-e`) only run `git add` + `git commit` inside their own worktree and **must not push** or **merge to the mainline**.
3. Run [`/code-review`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md) before committing; after committing, re-check the change with `git diff -- <explicit paths>` (`git commit -m … -- <path>` does not go through the index, so there is no need to inspect `--cached`).
4. **One writer per worktree (no exemptions)**: from the start of work on a worktree to its end, **only the one agent dispatched to that ticket may commit**. Anyone who wants to commit their own documents / notes **must not** do it in a worktree where an engineer is working — use the main worktree or open another one. **A concurrent commit raises no error; it just sweeps someone else's changes into your commit**, and you only find out afterwards with `git show --stat`, by which time it is already in history.

   - **How to apply**: run `git status` before committing to see whether someone else has uncommitted changes; if so, switch to `git commit -- <your own paths>` and **do not `add` first**; if you find someone else's changes in the same worktree, stop and ask devm — do not decide on your own that "it should be fine".
5. **Push cadence (devm)**: ① **push to GitLab at least once per completed ticket** (address from `DMT_GITLAB_SERVER` / `DMT_GITLAB_PORT` in `.env`, template in `.env.example`), the push message containing `{spec-seq}-ticket-{slug}` and a one-line result (`publish.sh` pushes to both remotes `gitlab origin` by default: GitLab primary, GitHub mirror; use `--remotes gitlab` to push to GitLab only); ② **at least once an hour**, sweep `git status --porcelain` and, if any file is new or modified, commit by explicit path and push (no need to wait for the ticket to close out). Summarize the sweep and push result in one line of the next report (what was pushed, what was skipped, and why).
   - Command: `bash dmt-director/scripts/publish.sh -m '<message>' -- <explicit paths...>`; `--auto` enumerates the changed paths from `git status --porcelain` (still explicit paths, never `git add -A`); `--no-push` commits only.
   - **③ While a branch is waiting to merge, push no commits to `master`** (documentation / policy ones included). Root cause: any movement of master forces the pending branch to rebase again ⇒ every commit sha changes ⇒ **sha-based registries (the authorization surface) must be re-pinned**, and every sweep / comparison reading already taken goes stale. **Source** = the measured evidence from devm pushing the policy document `17facd63` after the 104 merge (it forced the fix branch to rebase again and triggered the `t068` S1.3 re-pin). ⇒ **Close-out order: land and merge all of the branch's fixes / evidence first, and push the master-side documents last.**
6. **On a merge conflict, "take main" (`checkout --ours`) holds only when main is a strict superset of the branch.** The test is not who changed more, but **an item-by-item comparison of "which lines each side has that the other does not"**; as soon as one item exists only on the branch, you must merge by hand.

   - **How to apply**: before merging, produce a two-sided difference list (`git diff --stat main...branch` file by file, or pre-judge with `git merge-tree`); after merging, **diff once more against the branch version** and confirm that the only differences left are "lines unique to main" and "the few lines merged by hand", with everything else byte-identical.

### 5.2 Parallel sub-agents

1. Do a **dependency analysis** before dispatching: only tasks without dependencies are suitable for parallel work; tasks that share files, share a build target, or have an ordered acceptance relationship **must be serialized**.
2. **Manager-layer path (hard constraint)**: `devm` / `anam` **always dispatch engineer sub-agents directly** — `devm` dispatches `dev-e` (one worktree per ticket), `anam` dispatches `ana-e`, **opening no intermediate-layer pane** (the team-lead layer has been removed). Engineer sub-agents are reclaimed when the task closes out.
3. **For tasks without dependencies, always fill every subagent slot in parallel (`director` / `devm` / `anam`; user ruling 2026-11-04, overturning "on demand, dispatch fewer")**: when tasks are **independent** (other than sharing a file surface / shared input / shared build target / ordered acceptance) ⇒ **fill every slot, up to the harness concurrency cap** (`max_subagents_conc` in `harness_matrix.yaml`, read via `dmt_concurrency_cap`: codebuddy 8/env, claude 10, codex 8), and **do not keep a serial fallback of your own**. Serial execution is **only** for real dependencies (shared files / build target / ordered acceptance / the same device / the same REA session) and for the worktree single-writer rule in item 7, **and the reason must be stated**. Sub-agents are reclaimed when the task closes out.
   - **Means**: cbc uses the **teammate form** (`Agent` with a `name`); pi uses the dynamic workflow `runs.all` (the `agent` field set to `delegate`); Codex dispatches in parallel with `spawn_agent` and collects results with `wait_agent`; inside a herdr session, if Codex lacks these interfaces it does only its own pane role's work and does not create nested panes. **Dispatch prompt templates and per-harness hosting details: [`team/07b-dispatch.md`](07b-dispatch.md)**.
   - **Abolished items** (do not bring back): the 2026-11-02 wording "on demand, dispatch fewer, do small tasks yourself" is void; the saturation-mechanism scripts — booking the ledger before starting, splitting each wave by the cap, counting concurrency slots, accounting on the first line of a report plus its reason whitelist — stay deleted and must not be restored.
4. **Product work (director dispatches `pde{n}` itself)**: the product line has no pane and no team-lead layer, so **for product units without dependencies always fill every `pde{n}` slot in parallel** (one `pde{n}` per unit, all units without dependencies dispatched at the same time, using the means from item 3); the same applies to `director`'s pre-review check.
5. Every dispatch prompt must state explicitly: inputs (artifact paths), boundaries, expected artifacts, report requirements, `timeoutMs` (no shorter than 45 min for long chains), and **file-writing discipline** (to change bash use a single-quoted heredoc / Write/Edit; never put a script body inside a JS template string; an Edit's `oldString` must be unique). **Fill in the skeleton and the reviewer variant from [`team/07b-dispatch.md`](07b-dispatch.md) — do not improvise.**
6. **End the turn immediately after dispatching** sub-agents; wake on the completion notification or the harness's wait primitive, then verify; Codex waits in the parent turn with `wait_agent` instead of polling from a shell.
7. Each development engineer gets **one git worktree** and edits and commits only inside it; the main worktree is read-only.
8. A sub-agent's results may be written into authoritative documents or used to move to the next step only after **the level that spawned it** has verified the evidence; managers do not take an engineer's raw report at face value.
9. **One sub-agent, one unit queue (rule established after the 2026-10-27 incident; post-mortem in `logs/2026-10-27-serial-queue-incident.md`)**:
    - **An in-flight sub-agent accepts only corrections / narrowings of the same unit**; **a new unit always gets a new sub-agent** (a separate worktree), and you **must not** append it with `SendMessage` to build a queue.
    - **Build a "file-surface matrix" before appending**: one line per item, `unit | files touched | overlaps an in-flight unit`. Only an overlap justifies queuing (and the specific overlapping file paths must be listed); no overlap ⇒ **dispatch a new sub-agent immediately**.
    - **Queued messages go stale**: an append that depends on a superior's arbitration must either state "the latest ruling prevails" or wait for the ruling to land before dispatching; otherwise the sub-agent completes a whole round against a specification that has already been voided.
    - **Criterion (out of bounds ⇒ new dispatch)**: it is a violation for the same sub-agent to receive an assignment of a second new unit (UI reading `N queued ≥ 2`).
    - **The sole criterion for reuse vs a new dispatch**: ask "will this requirement change the **acceptance surface** of what they are doing?" No ⇒ reuse (defect fix / narrowing); yes ⇒ new dispatch (even for the same ticket and topic).

### 5.4 Reading discipline (performance windows)

1. **The observation window must be defined explicitly, and diagnostic switches must be logged with the window**: any performance / timing comparison must state **the observation window and the run duration** — **instantaneous or windowed metrics are not health evidence** ("0 events inside the window" does not mean "no problem"; the standard phrasing is **re-measure after running ≥ 5 min**). Wherever a diagnostic / dump / sampling switch exists (off by default), **check its state value before opening the window** (e.g. `diagnostics_state`) **and write that value into the criteria line**; **readings taken with the window open must never be compared against readings taken with it closed, and never feed any conclusion**. (Measured example: with that switch on, one target project recomputed the raw sha256 every frame, costing about 13% of whole-process CPU and about 95% of the detect thread ⇒ the measured fps was about half the production setting; **the exact identifiers and values depend on the target project**.)
2. **Never compare absolute values across builds**: millisecond figures from different artifacts (so / APK / firmware / image) **cannot be compared with each other** (the build currently installed on the device, the corpus and the artifact in the repo come from three different sources); **ratios may be compared across builds, but a banner must say so** (e.g. "this window and the previous window are not the same build").
3. **A "stop" must be re-verified**: after issuing a stop command you must confirm **the target process has really exited** (e.g. `pidof <pkg>` is empty) before calling it stopped; **a subordinate's "already stopped" cannot be taken at face value**.
4. **A snapshot counts for this window only if it meets both conditions**: ① it is in **this window's manifest** (e.g. `new.list`); ② its **build hash** (e.g. `build_sha256`) is **consistent** with the other snapshots in the same window. Failing either ⇒ it is a **leftover from another round** and is forbidden in any reconciliation (including per-stage timings and fps).
5. **Hardware device write permissions (`devm` and `director` both allowed; user ruling 2026-11-04: first handed to devm, then opened to the director)**: any **write operation that has side effects on a hardware device** — installing / uninstalling artifacts, flashing firmware, overwriting files or configuration on the device, triggering device probes, force-killing device processes, changing device runtime parameters and the like — **may be performed only by `devm` or `director`**; `anam` / engineers / sub-agents are **all forbidden** (report to `devm` or `director` when needed; **do not delegate the authority** to an engineer). **Only one writer per device at any moment**: confirm nobody is using the device before starting. **Toolchains and device files follow what the target project actually uses** (not limited to Android: command-line tools such as `adb` / `fastboot` / serial port / network port / JTAG and device-specific files all fall under this). After any device operation you must report **verifiable evidence**: the hash of the artifact written (e.g. `sha256`) + the device-side version / update time + confirmation that the target process has really exited (e.g. `pidof` empty) — the exact fields depend on the project's device.
