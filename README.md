# dmt

> **Version 5.7.1 · 2026-10-27** — same number as the `version:` field in the four role `SKILL.md` files; when spot-checking, read this line first to confirm which version is loaded. A mismatch means the wrong install.

Role-skill repo for the dmt team: **the single maintenance point for the team definition and the four role skills**. Hierarchy: `director` (team lead & product manager) → department managers (`devm` / `anam`) → engineers (`dev-e` / `ana-e` / `pde{n}`).
**The product department is merged into the director**: when writing the PRD / SPEC / tickets the director summons `pde{n}` to write them (human documents are written by the director in person), and self-dispatches `pde{n}` / `reviewer{n}` sub-agents (the `dmt-pde` skill, occupying no tab and no pane); there is no product manager; the `devm` pane sits on the right side inside the director tab, and `anam` gets an independent tab.
**Managers dispatch engineers directly**: `devm` / `anam` always dispatch `dev-e` / `ana-e` sub-agents directly (`open on demand`, cap `min(8, cap)`); worktree creation, the implementation-level first pass and primary-source verification are closed out by the managers, and there is **no lead tier**.

> **Scope (read first)**: every rule in this document — role permissions, **write ownership (install / `git push` / merge)**, gates, pane lifecycle, inbox rules — applies **only to the "target project" managed by the dmt workflow** (the project root initialized by `init-project.sh`), i.e. the software the team is building.
> **It does not apply to maintaining the dmt skill repositories themselves** (`dmt` / `dmt-en` / other skill repos): a maintainer (human or another agent) may `git add` / `git commit` / `git push` directly, **without director authorization and without devm acting as the pusher**; likewise, the install permission only constrains device writes inside the target project.

**Three-layer naming**: the skill name carries the `dmt-` prefix (`dmt-director` / `dmt-pde` / `dmt-dm` / `dmt-am`) and is used by the skill registry, the install directory and the slash command; the runtime id carries no prefix (`director` / `devm` / `anam` / `pde{n}` / `dev-e` / `ana-e`, helpers are `{role}-helper`) and is used by pane labels, inbox directories and direction codes; prose and logs use the form of address (Director / Development Manager / Analysis Manager). **Never mix the three.**

**Single-line command**: each role talks only to its direct superior and direct reports; the director never skips levels to command engineers, managers never connect sideways, and every cross-department matter is relayed by the director. **Engineers are always sub-agents** (no pane, no cross-pane communication): they are always spawned directly by a manager (`devm` spawns `dev-e`, `anam` spawns `ana-e`, `open on demand`, cap `min(8, cap)`) — there is no pane-level channel between a manager and an engineer, only a parent-child sub-agent relation; `pde{n}` is spawned directly by `director`.
**Helpers (`{role}-helper`, a pure clone of the role, at most one per role)**: `director-helper` / `devm-helper` / `anam-helper` are **pure clones of the role** — the task is delivered with the spawn as a **one-shot dispatch**, and afterwards the helper **accepts no further input**; its work is a **one-way report** to the principal (`{role}`); a helper **has no inbox of its own** (it receives nothing) and **does not use doorbells**. **The lifecycle is maintained by the creator (the principal role)**: create it with `bash dmt-director/scripts/spawn-helper.sh <director|devm|anam>` (idempotent, supports `--dry-run` / `--no-start`; the helper tab label is fixed to `helper` (shared by the whole team), the pane label is fixed to `{role}-helper`, and it starts the harness on the principal's behalf and loads the **same-role skill**), self-heal a drifted label with a rename, and reclaim it when the task is done with `bash dmt-director/scripts/close-helper.sh <director|devm|anam>` (supports `--force` / `--dry-run`; **the helper tab is kept for reuse and is not closed with the pane**). **Exclusive actions are never delegated**: installation belongs to the `director` principal alone, and merge / push belong to the `devm` principal alone.

Members run inside Herdr (a terminal multiplexer for multi-agent work) and **identify peers by pane label** (the label equals the role name and is unique in the workspace; **not by position within a tab**, and pane ids are re-resolved before every send).
**Inter-role communication = inbox file + herdr doorbell**: the body goes into the receiver's `inbox/<recipient>/{seq}-{direction}-{slug}-{YYMMDDHHMM}.md` (project root, not under `docs/`), and herdr only carries one line ("you have a new message …"); the receiver **sends no receipt**: it first moves the file into `inbox/<self>/.doing/` with `msg-take.sh` (claim), then deletes it with `msg-done.sh` once done (details in `team.md` §1.3).
Workflow in one line: anam does the research (reviewed by the director) → the director fixes the acceptance criteria and summons `pde{n}` to write the PRD, SPEC and tickets (document-gate self-review) → devm takes the tickets and schedules them, and **devm / anam dispatch engineer sub-agents directly (`open on demand`, cap `min(8, cap)`), with the implementation-level first pass and source verification closed out by the managers** → devm finishes the tickets and reviews at the **code gate** → the director dispatches reviewer1…reviewer{n} by ticket count to accept devm's code item by item against the SPEC and ticket of the same spec-seq → on pass, notify devm to merge/push (reviewer{n} are sub-agents occupying no pane and loading no skills, with `/review` (= `/code-review`) written into the dispatch prompt, `open on demand`, cap `min(8, cap)`; **merge and push belong to devm alone**: `push at least once per completed ticket` and patrol unpushed changes `at least hourly`, and the code repository is managed by devm); on failure, send it back to devm for rework and **never merge/push first**. Installation (`adb install` etc.) is **only director may execute**. devm / anam may **work directly on the user's request and the tickets plan**, only notifying the director; the director **lets it pass by default and only steps in when something looks wrong** (unimpeded).

## Installing into a project

The folder name in this repo is the skill name (`dmt-director` / `dmt-pde` / `dmt-dm` / `dmt-am`); **when installing into a skill directory, copy under the same name**. The runtime ids (`devm` and friends) only label panes and name inboxes and do not change with the skill name.

```bash
# symlink install (recommended; follows updates from this repo)
bash dmt-director/scripts/install-skills.sh <project-root>

# copy install (the target project does not follow this repo)
bash dmt-director/scripts/install-skills.sh <project-root> --copy
```

The script does four things: ① creates `.agents/skills/` and symlinks or copies the four skill directories; ② links or copies the whole `dmt-director/` (including `scripts/`) into the project root — **script paths are always `dmt-director/scripts/…`**, and the old `<project-root>/scripts/` is dropped; ③ copies `team.md` to `docs/team.md` (the machine check reads this copy, which must be the same version as the original); ④ calls `init-project.sh` to create the directories, write `.gitignore` and run the machine check.

Symlinking the whole role directory exposes the contract, the notes and the checker script under `dmt-director/` without affecting skill loading.
When installing into a user-level skill directory of another harness (codebuddy / codex / opencode …), the rule is the same: **the folder name is the skill name**.

## Checker

```bash
bash dmt-director/scripts/check-dmt-doc-paths.sh <project-root>   # checks the current directory when the argument is omitted
# override with DMT_SKILLS_DIR when the skills are not under <project-root>/.agents/skills (default on line 9 of the script)
```

**Eighteen** criteria (plus two special groups, 2b / 4c, 20 assertion groups in total): ① the six unique directories + the root `inbox/` exist (**the director fills gaps at initialization**, see `team.md` §3.1); ② the four skills (`dmt-director` / `dmt-pde` / `dmt-dm` / `dmt-am`) each point at their own unique directory (PRD / SPEC / tickets / human documents belong to `dmt-director`; `dmt-pde` is the `pde{n}` sub-agent skill); ③ **the helper pure-clone semantics and the reclamation action are registered** (the contract contains `one-shot dispatch`, `accepts no further input`, `one-way report`, `has no inbox of its own`, `never close before collecting` and `only panes may be closed`; the contract and `dmt-director` / `dmt-dm` / `dmt-am` contain `close-helper.sh`; `spawn-helper.sh` contains `one-shot dispatch`); ④ **identity resolution is registered** (the contract and all four skills contain `pane label`, and the contract contains `not by position within a tab`); ⑤ **the manager-tier parallelism criterion is registered** (`dmt-dm` / `dmt-am` contain `must run in parallel`, and the contract contains `dispatch sub-agents for every dependency-free task` and `min(N, CAP)`); ⑥ **manager direct dispatch and on-demand dispatch are registered** (the contract contains `min(8, cap)` (cap = the maximum number of agents the harness supports; the effective CAP = `min(8, cap)`, defaulting to 8 when undetectable, and N > CAP is advanced in batches; at any moment the in-flight instances of the director / managers are always ≤ `min(8, cap)`); `dmt-dm` / `dmt-am` contain `open on demand`, `saturate` and `teammate`); ⑦ **installation and push ownership is registered** (installation: the contract contains `only director may execute` (in backticks); push and merge: the contract contains `merge and push belong to devm alone`, `dmt-dm` contains "push and merge belong to devm", `dmt-director` contains `does not push on their behalf`, the negative assertion that push belongs to the director alone must not appear, and the contract contains `push at least once per completed ticket` and `at least hourly`); ⑧ **the mattpocock mandatory skills are registered per role** (the contract contains `mandatory` and the role table; on the skill side `dmt-director` / `dmt-pde` / `dmt-dm` / `dmt-am` each contain their own mandatory skill names (`dmt-dm` contains `/code-review`, `dmt-am` contains `/research`, etc.); the execution skills absorbed by `dev-e` / `ana-e` are registered in the **contract role table `dev-e` / `ana-e` rows** (the contract contains `/tdd`, `/implement`, `/diagnosing-bugs`, `/rea`, `/grilling`, `/grill-me`, `/grill-with-docs`, 7 contract assertions in 4e)); ⑨ **file claims are registered** (the contract contains `file claim` and `file-claim`, each of the four skills contains `file-claim`, and the script exists); ⑩ **review gate ownership is registered** (the contract and `dmt-director` contain `document gate`, the contract and `dmt-dm` contain `code gate`, and `dmt-director` contains `does not replace`); ⑪ **the cbc-herdr common skill is registered** (each of the three pane-role skills contains `cbc-herdr`); ⑫ **skill links match upstream** (the contract and all four skills contain `raw.githubusercontent.com`); ⑬ **deterministic actions are scripted** (eighteen scripts exist and are executable, including `launch.sh` / `probe-cap.sh` / `fanout.sh` / `parallel-guard.sh` / `spawn-helper.sh` / `close-helper.sh`); ⑭ **the three-state inbox is registered** (the contract contains `.doing/` and `.seq`, and each of the three pane-role skills contains `msg-take.sh`); ⑮ **dispatch first, the concurrency ledger and reporting on completion are registered** (the contract and the three dispatching skills `dmt-director` / `dmt-dm` / `dmt-am` contain `dispatch first` and `concurrency ledger`; the contract and `dmt-director` / `dmt-dm` / `dmt-am` contain `report on completion`; the contract contains `dispatch compliance`); ⑯ `this contract is fully registered`; ⑰ **the contract header carries a version and date matching the four skills** (`team.md` header `Version X.Y.Z · YYYY-MM-DD`, all four `SKILL.md` `version:` fields equal to it, script 4m); ⑱ `negative samples are rejected` (**only the §3 landing registry table** of the contract is inspected; historical traces in §8 do not count). **Rerun after changing the path convention, pane lifecycle, parallelism wording, role hierarchy, write permissions, mandatory skills, file claims, review gates, common skills, skill links, inbox lifecycle or script interfaces.**

## Maintenance

- This repo is the **single maintenance point** for dmt; consumers keep no copy. With symlinks, skills and the contract update with the repo and take effect immediately (no reinstall needed).
- Contract references inside the skills do not depend on relative paths (written as "`dmt-director/team.md` (this repo; `docs/team.md` once installed)"), so symlink installs never break.
- A change to a script interface (arguments, output, exit codes) counts as a contract change and must be mirrored in the four skills and in script group 4m.
- Harness-side skills required: `herdr` (pane control and label resolution), `cbc-herdr` (CodeBuddy status reporting), `pi-subagents` (pi harness only; cbc uses Agent/team sub-agents), plus mattpocock's [`/to-spec`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-spec/SKILL.md), [`/to-tickets`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-tickets/SKILL.md), [`/code-review`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md), [`/tdd`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/tdd/SKILL.md), [`/research`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/research/SKILL.md) and friends (installation and fallback in `team.md` §1.4).
